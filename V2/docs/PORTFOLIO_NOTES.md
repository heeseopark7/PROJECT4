## 0. 포트폴리오 구성 (계획서 8장)
- **첫 화면(README):** 한 줄 주제, **버전 × 지표 비교표 하나**, 클럭별 슬랙 그래프 하나. 30초 안에 흐름이 보여야 한다. 슬랙 그래프는 클럭 sweep(V3 이후) 데이터가 필요하므로 가안에서는 자리만 둔다.
- **버전 페이지:** 가설 / 변경 내용 / 결과 / 해석 / 한계 5칸 (V1은 부록, V2~).
- **부록 A:** 패드 포함 완성본(V1)의 합성, PnR, post-layout 시뮬. **부록 B:** MCU RTL 상세 해설 보고서.
- 핵심 서사(한 줄): **자작 MIPS MCU를 RTL부터 GDS까지 구현하고, 타이밍 병목을 분석해 버전별로 한 가지씩 개선하며 PPA 변화를 측정하고 해석했다.**
- 평가 포인트는 RTL이 아니라 **합성~PnR~STA를 직접 다뤘다는 근거와 분석 사고 과정**이다. "왜"를 설명할 수 있어야 한다.

## 1. 버전과 트랙 (헷갈리기 쉬움)
- V1 = 패드 포함 완성본(`mcu_pad_top`, 완료). V2 = **패드만 뺀 코어 단독 기준선**(`mcu_core_top`, RTL 변경 없음, 완료). V3 = 가산기 교체(진행 예정).
- **V1과 V2의 슬랙/전력/면적은 직접 비교하지 않는다** (계획서 4장). 패드가 칩 면적의 91%, 전력의 대부분을 차지하고 밀도가 9.5%라 물리 비교가 무의미하기 때문. V2를 새 기준선으로 다시 측정했다.
- V2의 원칙은 **"V1과 패드 유무만 다르고 나머지는 똑같이"**였다. 의도된 차이 목록은 `V2/README.md`에 있다 (합성 SDC 패드 줄, floorplan 여백 30 µm, `editPin` 핀 배치, 바깥 링 제거, PnR용 SDC에서 `set_ideal_network` 제거).

## 2. 단계별 해석 노트

### 2.1 합성 (Genus, 10 ns)
- **본 것:** slack +1.2 ps, TNS 0, FF 1,816, 인스턴스 5,235 (순차 1,816 / 조합 3,419), 셀 면적 21,819 µm². 계층: RAM 48.1%, UART 23.7%, CPU 19.6%, SPI master 3.5%, SPI slave 3.1%, ROM 1.4%. 합성 4분 11초. 순차 소자가 면적의 66.3%.
- **해석:** V1 10 ns의 코어(21,856 µm², FF 1,816, 인스턴스 5,241 상당)와 0.17% 차이, 모듈별 비율도 같다 → **래퍼가 합성 구조를 바꾸지 않았다.** `check_design`도 V1과 같다(Assigns 98, Constant 1,869 등). 차이는 `Libcells with no LEF` 4→0, `LEF cells with no libcell` 91→78 뿐이고, 패드 라이브러리/LEF를 읽지 않아서 생긴 것으로 보인다 [추정].
- **slack이 +1.2 ps인 이유:** 느슨한 제약(10 ns)에서 Genus가 **여유를 면적 절약에 써서 slack을 0에 맞춘다.** 따라서 "slack 여유 = 진짜 마진"이 아니다 (3장 Q3 참고).
- **최악 경로:** `r_pc_reg_5 → u_mcu_top/uut5/uut2/r_count_reg_4`. **`uut5/uut2`는 `tx_fifo`의 카운터**이지 보레이트 카운터가 아니다 [확인: 계층 표에서 `uut5/uut1 = baud_gen`, `uut2 = tx_fifo`, 경로에 `w_tx_push`].
- **가산기 구조 [확인]:** ADDFX1 6개, ADDHX1 51개 (V1은 ADDHX1 46개; `sccpu` 안은 ADDFX1 6 + ADDHX1 7로 V1과 동일, 차이는 CPU 밖 `interrupt_logic` 4→9). 최악 경로의 가산기는 ADDFX1 체인이 아니라 `sub_158_49_Y_add_166_49_*` 셀과 AOI2BB1 계열 게이트열이다. V1 PPT의 "32비트 ripple-carry 약 1.67 ns"는 20 ns/5 ns 합성에서 본 구조이고 10 ns 넷리스트는 다르다.
- **합성 전력 0.644 mW:** register/logic은 V1 10 ns 코어(약 0.80 mW 중 register 0.437, logic 0.170)와 거의 같고 **clock 항목만** 다르다 (V1 0.19 mW, V2 0.0006 mW). `clk` 포트가 ideal network라 클럭 전력이 계산되지 않은 것으로 보인다 [추정]. 합성 전력은 비교에 쓰지 않고 Innovus 결과를 쓴다.
- **합성 SDC 경고 SDC-208:** `fast_vdd1v0` 라이브러리를 읽지 않아 `set_operating_conditions`의 min 코너가 무시된다. V1에서도 같은 경고. 합성은 slow 단일 코너, hold는 PnR/STA에서 FF 코너로 본다 [확인].

### 2.2 EC 1회차 (RTL ↔ 합성)
- **본 것:** PASS. 입력 7/7, 출력 8/8, FF 1,816 모두 Equivalent. RTL에만 있는 792개 (Extra 32 + Unreachable 760). Design ambiguity 1건(중복 모듈 정의).
- **해석 (FF 2,608 → 1,816):** 프로그램이 ROM에 고정되어 쓰이지 않는 레지스터와 관찰되지 않는 PC 비트가 합성에서 제거된 것이다. **792 = 24개 미사용 레지스터 × 32비트(768) + 관찰되지 않는 PC 비트 24개**로 계산이 맞아떨어진다 [추정: 계산 일치, 직접 매핑은 확인 안 함].
- **Design ambiguity 1건:** V1과 같은 값이라 래퍼 때문이 아니다. 원인은 확인 못 했다. `read library -both`로 slow/fast 셀 모델을 둘 다 읽어 같은 셀 이름이 중복되는 것일 수 있다 [추정].

### 2.3 pre-layout 시뮬 (합성 SDF)
- **본 것:** PASS (8645 ns), 첫 UARTTXD 하강 +0.83 ns, 첫 SCLK 상승 +0.36 ns, SDF scope `tb_mcu_top.u_mcu_core_top`, 미적용 488건은 전부 REMOVAL.
- **해석:** V1(+1.773 / +1.392 ns)보다 작은 것은 **출력 패드 지연이 없기 때문**으로 보인다 [추정: 차이가 약 0.9~1.0 ns로 패드 지연 규모]. 프레임 길이(5760 ns)와 SCLK 주기(160 ns)는 그대로 → 기능은 지연에 영향받지 않는다.

### 2.4 PnR (Innovus) 단계별
**0 InitDesign:** die 251.6 × 249.85 µm, 코어 191.6 × 189.81 µm = 36,368 µm². 합성 셀 면적 21,819 ÷ 36,368 = **0.600**, utilization 목표와 정확히 일치. 핀 15개를 `editPin`으로 4변에 배치(위 3, 좌 4, 우 4, 아래 4; GDS에서 Metal3 8개 + Metal4 7개). prePlace WNS +3.138 ns, 전체 경로 3,640개(reg2reg 3,140 + IO 502)로 V1과 **개수까지 동일**, Density 59.996%. (V1 prePlace +3.342 ns, Density 9.530%.)

**1 PowerPlan:** 코어를 둘러싼 이중 링(바깥 VSS, 안쪽 VDD) + 수직/수평 스트라이프. 링은 코어 경계에서 약 20 µm 바깥이고 die 경계까지 약 10 µm 여유 → **여백 30 µm이 맞았다.** DRC 0, 연결성 0. 두 번째 `verifyConnectivity -type special`의 `IMPVFC-96` 메시지는 **배치 전이라 셀이 아직 안 놓였다는 안내**이고 위반이 아니다. 로그의 "Processed 5000 nets"는 전체 net 수가 아니라 진행 메시지로 보인다 [추정; V1 문서의 "5000개 net 검사" 표현은 피한다].

**2 PlaceOpt:** 배치 5,223개(합성 5,235와 12개 차이, 원인 미확인), 배치 밀도 59.94%(`place_design` 직후) → 60.603%(`place_opt` 후; 최적화로 셀이 커지고 버퍼가 추가됨). **V1 문서의 9.52% vs 9.9%도 같은 시점 차이다** (밀도 값은 시점을 반드시 같이 쓴다). 혼잡도 Overflow 0 (사용률 H 2.1%, V 3.9%). preCTS WNS +0.399 ns, TNS 0, **DRV 모두 0** (V1은 −0.352 ns, 위반 3개, max_tran 33 net). 이유는 확인 못 했다(코어가 작아 배선이 짧아진 영향일 수 있으나 추정). Density map은 숫자가 있는 칸이 0.760~0.892이다(일정 밀도 이상인 칸만 표시되는 것으로 보임 [추정]).
- 재실행 이력: 0~2단계는 PnR용 SDC로 한 번 재실행했고(WNS +0.397 → +0.399, Density 60.475 → 60.603%), 변화는 `clrn`이 ideal이 아니게 되며 버퍼가 몇 개 추가된 영향으로 보인다 [추정].

**3 CTS/최적화:**
- **클럭 버퍼 138개**(V1 176), 인버터 1개, 최대 non-leaf fanout 22, leaf fanout 21, 최대 길이 253.93 µm, FF 1,816개(posedge 1,799 + negedge 17). 트리는 **루트 → 1단 버퍼 약 22 → 말단 버퍼 약 116 → FF**의 3단(133 = 138 − ... 아님, 22 + 116 = 138은 평균 fanout 값에서 역산한 분해 [추정]).
- **스큐:** setup 0.097 ns, hold 0.039 ns (V1 0.165 / 0.044). 삽입 지연 평균 0.477 ns (V1 1.82 ns). SDC의 클럭 latency 설정(0.2 + 0.2 = 0.4 ns)이 CCOpt의 ID Target `0.400`이고, V2는 거기에 가깝다. 목표 스큐 0.01 ns는 V1처럼 못 맞췄다(10 ns 주기의 약 1.0%).
- **V1과 트리 모양이 다른 이유 [확인+추정]:** V1은 클럭 트리의 루트가 **입력 패드 `PADDI`**(클럭 로직 면적 14,400 µm², 2.387 pF)이고 패드가 die 가장자리, 코어가 중앙이라 트렁크 배선 2,820 µm와 직렬 버퍼 기둥이 생겼다. V2는 핀이 코어에서 30 µm라 곧바로 분기한다. 설정 차이가 아니라 **패드 유무의 결과**다.
- **타이밍 흐름 (setup WNS):** preCTS +0.399 → CTS 직후 +0.034 → 최적화 후 +0.275 ns. CTS 후 여유가 줄어드는 것은 이상적이던 클럭이 실제 트리 지연/스큐를 갖게 되기 때문으로 보인다 [추정]. V1은 +0.099 → +0.148. CTS 직후 값은 `optDesign -postCTS`의 Initial Summary이며 `ccopt_design` 직후 `timeDesign`과 미세하게 다를 수 있다.
- **hold:** 최적화 후 +0.001 ns (reg2reg +0.053, IO +0.001). **IO hold가 얇은 이유는 4장 서사 6 참고.**
- Density는 CTS로 60.603 → 61.588%(약 358 µm², 클럭 버퍼 312 µm² 포함), 최적화로 61.828%.

**4 Route:** DRC 0, 연결성 0. postRoute setup +0.348 ns(reg2reg +0.348, IO +8.203), hold +0.011 ns(reg2reg +0.054, IO +0.011), DRV 0, Density 61.839%. 정적 전력 **0.765 mW**(내부 0.548 / 스위칭 0.216 / **누설 0.00046 mW**). 누설이 V1(0.612 mW, 11.4%)보다 1,300배 작은 것은 **V1 누설의 거의 전부가 입출력 패드**였기 때문이다 [확인: 합성 전력 리포트에서도 패드 누설 6.1e-4 W vs 코어 4.4e-7 W]. 전력 계산에는 V1에서 물려받은 `-period 8.0`(설계 클럭 10 ns)이 쓰였으므로 **캡션에 "8 ns 기준"을 써야 한다.**

**5 ChipFinish:** 필러 7,384개(FILL1 2,262 / FILL2 2,289 / FILL4 1,495 / FILL8 668 / FILL16 327 / FILL32 149 / FILL64 194; **작은 필러 82%**: 밀도 62%라 빈 공간이 잘게 나뉨. V1은 밀도 10%라 FILL64가 대부분). 필러 후 DRC 0, 연결성 0. 산출물: `.v` 0.62 MB, SDF 3.75 MB 두 개, `.sdc` 5 KB, GDS 8.1 MB (V1: 1.3 / 3.8 / 10.7 MB). GDS는 인스턴스 13,198, 핀 15, net 68,073, via 44,191.

### 2.5 EC 2회차 (합성 ↔ PnR)
- **PASS.** 비교점 PO 8 + DFF 1,816 = **1,824 모두 Equivalent**, 입력 7/7, Unmapped 없음, Design ambiguity 1건(V1과 동일). Revised에만 PnR이 추가한 셀이 최상위에 22개, `u_mcu_top`에 144개(Golden 58개) 있고 비교점이 아니라서 영향 없다.
- 최상위 22개는 클럭 버퍼가 아니라 **입출력 쪽 버퍼**(입력 `clrn`에 약 10개, `SLVCSN`에 4개의 지연 버퍼 열, 출력의 버퍼/인버터 쌍)로 보인다 [추정: Tempus 스키매틱 모양]. 클럭 버퍼 138개는 `u_mcu_top` 안에 있다.

### 2.6 post-route Tempus
- **본 것:** setup +0.347 ns (Innovus +0.348과 일치), hold +0.011 ns (일치). 분석 커버리지 Setup 3,144/3,144, Hold 3,144/3,144 Met, 위반 0. 실제 신호 net 5,906개 100% annotated(V1 6,163개), 미연결/무부하 688개는 타이밍 대상 아님. Recovery/Removal 505개 중 488개 Met, 17개 Untested(상수 경로). `check_timing` 경고는 `no_drive` 14건뿐이다.
- **`no_drive` 14건:** V1은 2건(입력 7개 중 `clk` 1개 × 2). V2는 구동 셀 대신 `set_input_transition`을 써서 입력 7개 × 2 = 14건 [추정: 계산 일치]. 분석에 영향 없음.
- **setup 최악 경로 [확인]:** `r_pc_reg_7 → 명령어 ROM → CPU 디코드/연산 → 주소 디코드 → UART 쓰기 디코드 → tx_fifo r_count_reg_4`, 데이터 경로 9.43 ns:
  | 구간 | 지연 | 비율 |
  |---|---|---|
  | PC 클럭→Q | 0.32 ns | 3% |
  | 명령어 ROM(`uut2`) | 1.41 ns | 15% |
  | CPU 디코드+연산(`uut1`) | 4.71 ns | 50% |
  | └ 가산기(`sub_158_49...`, `g201xx`) | **약 3.2 ns** | **34%** |
  | 주소 디코드(`u_mcu_top` 상위 게이트) | 1.42 ns | 15% |
  | UART 레지스터(`uut5/uut6`) | 0.62 ns | 7% |
  | TX FIFO(`uut5/uut2`) | 0.97 ns | 10% |
  이 경로가 **V1 PPT의 "PC → ROM → 가산기 → 주소 디코드 → FIFO" 서술을 직접 확인**해준다.
- **hold 최악 경로 [확인]:** 입력 포트 `UARTRXD` → 지연 버퍼 `FE_PHC611/614/620/626/632/639/643_UARTRXD` 7개(CLKBUFX4/X2) → 동기화 FF `r_rxd_s1_reg`. 입력 지연 최소값이 0.010 ns뿐인데 FF 쪽 클럭이 약 0.17 ns 늦게 도착해서 hold를 맞추려고 `optDesign`이 지연 버퍼를 넣었다(도착 0.010 → 0.182 ns, 필요 0.170 ns, slack +0.011). V1은 입력 패드 지연 덕에 이 수정이 필요 없었다. **패드를 뺀 V2에서 처음 생긴 특징**이라 "해석" 소재로 좋다. hold 여유가 1 ps(3단계)였다가 배선 후 11 ps로 올라갔다.
- **`Design Mode: 65nm` 표시:** 스크립트에 `setDesignMode -process`가 없어 기본값이 쓰이며 V1과 동일 조건이다(V1 PPT 16번의 "90nm"도 같은 맥락). 기생 성분은 QRC 기술 파일에서 오므로 영향은 제한적일 것으로 보이나 [추정] **"한계"에 기록**한다.

### 2.7 post-layout 시뮬 (worst/best, Tempus SDF)
- **본 것:** 둘 다 PASS(8645 ns). SDF 적용률: 경로 지연 **91.56%**(14,529/15,868), 타이밍 체크 **82.30%**(10,442/12,687, V1과 개수까지 동일), 에러 0. 첫 UARTTXD 하강 worst +0.941 ns / best +0.241 ns, 첫 SCLK 상승 worst +0.891 / best +0.22 ns. 프레임 길이(약 5760 ns), SCLK 주기 유지. `MTM control` MAXIMUM/MINIMUM 확인.
- **미적용 항목:** 리셋 FF의 **RECREM** 검사만(로그에 500건 표시; xmelab 요약 경고 505건은 경고 한도 1000에 걸려 5건이 생략된 것으로 보임 [추정], 표시된 500건은 모두 RECREM). 원인 [확인: 셀 모델 소스]: `DFFRX1` 모델은 리셋 핀에 **별도의 `$recovery`와 `$hold`(removal 역할)** 체크(한계 0)를 두고, Tempus SDF는 이를 **`RECREM` 결합 항목**으로 줘서 시뮬레이터가 매핑하지 못한다. 통계의 `$hold` 595, `$recovery` 595가 0%인 것도 같은 현상이다. **리셋 recovery/removal은 SDF 시뮬로 검증되지 않지만 STA(Tempus)에서 위반 0**이다. 시뮬 기능 PASS는 영향 없음. (V1 문서의 "셀 모델에 해당 체크가 없어서"는 `$hold`/`$recovery`에는 방향이 틀린 설명이다.)
- **지연이 V1보다 작은 이유:** V1 post worst +3.458 ns vs V2 +0.941 ns. 출력 패드 지연이 없고 클럭 트리 삽입 지연도 작아서(1.82 → 0.477 ns)로 보이나 정확한 분해는 확인 못 했다. pre→post 증가폭이 V1(+1.7 ns)에 비해 V2(+0.11 ns)에서 작은 이유도 미확인.
- 사소한 경고: `SHMODBP`/`SHMNOSO`(파형 `dump` 폴더 없음), `CUVWSP`(넷리스트 28,219번 줄 부근 인스턴스의 출력 포트 1개 미연결 — 디버그 출력으로 추정), `NOMTDGUI`. 결과와 무관.

## 3. 면접 질문별 답변 소재 (계획서 11장, V2 데이터 기준)
1. **최악 경로가 왜 PC → ROM → 가산기 → 디코더 → FIFO enable이었나? 한 클럭 안에 무엇이 끝나야 하나?** 단일 사이클 CPU라서 명령어 인출(ROM 비동기 읽기) → 디코드 → ALU(가산기) → 데이터 주소로 쓰이는 `aluout` → 주소 디코드(RAM/APB 선택) → UART 레지스터 쓰기 enable → TX FIFO 카운터까지가 **한 클럭에 끝나야** 한다. 2.6장 표(9.43 ns, 가산기 34%)로 설명.
2. **가산기를 바꿨더니 슬랙은 얼마나 좋아졌고 면적은 왜 늘었나?** V3 결과로 채운다 (아직 없음).
3. **setup 슬랙 +0.441 ns는 어느 정도의 여유인가? 클럭을 줄이면 어디서 먼저 깨지나?** **슬랙은 진짜 마진이 아니다.** 10 ns에서는 툴이 여유를 면적 절약에 써서 slack을 0 근처로 맞춘다(V2 합성 +1.2 ps). V1 PPT의 합성 sweep(로그 대조 전 수치)은 4 ns(+0.2 ps, 면적 +19%)까지 닫혔다. 실제 한계는 sweep으로 찾아야 한다 (V3 이후).
4. **패드를 빼면 PnR 결과 해석이 어떻게 달라지나? 왜 두 트랙의 슬랙을 직접 비교하지 않았나?** 패드가 칩 면적의 91%·전력의 대부분을 차지하고 밀도가 9.5%라 혼잡/CTS 비교가 무의미했다. 패드를 빼니 밀도 60%, 클럭 트리 단순(버퍼 138, 삽입 지연 0.477 ns), 누설 전력 1,300분의 1, 입력 hold 수정 버퍼가 새로 등장. 입력 지연/구동 모델이 달라 IO 경로는 직접 비교 불가.
5. **FF 2,608개가 합성 후 1,816개로 준 이유?** 2.2장 (792개 = 미사용 레지스터 24×32 + 관찰 안 되는 PC 비트 24 [추정]; EC에서 Extra 32 + Unreachable 760).
6. **V4에서 경로를 끊었더니 사이클 수는 어떻게 변했나?** V4 결과로 채운다.

## 4. "문제를 발견하고 해결한" 서사 (면접/해석 소재)
1. **범위 일탈을 스스로 되돌림:** V1과 같아야 하는 SDC의 I/O delay를 임의로 1.0 ns로 바꿨다가 "패드 외에는 동일" 원칙으로 V1 값(0.1/0.01 ns)으로 복구하고 재합성. 교훈: 한 번에 하나.
2. **근거 없는 값의 출처 확인:** 출력 부하 20 fF를 임의로 넣었다가, V1 합성 리포트(`02_report_port.rpt` External Loads **3.0**)에서 실제 값을 찾아 3.0 fF(`set_load 0.003`)로 교체. 단위는 합성 SDC 출력의 `set_load -pin_load 0.003`으로 확정 [확인].
3. **예측 후 검증 (ideal network):** V2는 패드가 없어 ideal network로 지정된 포트 net이 곧 FF를 구동하는 net → CTS가 버퍼를 만들지 않을 수 있다고 **실행 전에 예측**했고, PnR용 SDC에서 `clk`, `clrn`의 `set_ideal_network`를 제거(합성 SDC는 그대로)한 뒤 CTS에서 **버퍼 138개 생성**을 확인했다. 0~2단계를 한 번 재실행했고 합성/EC/시뮬은 영향 없음.
4. **내 추정의 오류를 데이터로 정정:** 합성 전력을 "V1 20 ns와 5 ns를 보간하면 10 ns는 약 1.2 mW"라 보고 V2(0.644 mW)가 이상하다고 했지만, 레포에 있던 V1 10 ns 실측 리포트와 비교하니 register/logic은 거의 같고 **clock 항목만** 달랐다(보간이 틀림).
5. **SDF 적용률 검증 (V1 사고 재발 방지):** V1에서 SDF가 0.17%만 적용됐는데도 시뮬이 PASS였던 경험을 바탕으로 V2는 로그로 적용률(91.56%)과 미적용 사유를 확인. RECREM 미적용을 **셀 모델 소스까지 열어** `$recovery`/`$hold`와 형식 불일치임을 확인하고, 해당 체크는 STA에서 위반 0임을 근거로 인정.
6. **hold 여유가 얇은 이유를 경로로 확인:** 3단계 끝에서 IO hold가 1 ps → 4단계 후 11 ps → Tempus 경로에서 입력 `UARTRXD`에 hold 수정 버퍼 7개가 들어간 것을 직접 확인 (입력 지연 최소값 0.01 ns가 원인). 두 툴(Innovus, Tempus)의 setup/hold가 일치(+0.348/+0.347, +0.011/+0.011).
7. **이전 버전 문서의 오류 발견:** V1 PPT에서 "UART 보레이트 카운터"라 부른 끝점이 실제로는 TX FIFO 카운터임을 계층 표와 `w_tx_push`로 확인 (5장).
8. **가설의 전제 검증 (가산기):** 계획서는 "RCA 병목"을 전제했지만 10 ns 넷리스트에는 ADDFX1 체인이 없고 AOI 게이트열이다. 그래도 가산기 구간이 최악 경로의 34%(약 3.2 ns)임을 post-route 경로로 확인해 V3 가설의 근거로 삼음.

## 5. 알려진 한계 / 미확인 (포트폴리오 "한계" 칸에 쓸 것)
- Design ambiguity 1건의 원인 미확인(V1과 동일).
- 합성(Genus)과 PnR 초기(Innovus) 간 지연 추정 차이(V1: 같은 ADDFX1 체인 단당 약 51 ps vs 185 ps) 원인 미해결. 스크립트에 `setDesignMode -process`가 없고 Tempus가 `Design Mode: 65nm`을 표시 — V1과 동일 조건, 별도 실험 과제.
- 전력은 활동도 0.2, 계산 주기 8 ns(V1 물려받음, 설계 클럭 10 ns) 정적 분석. 합성 전력은 clock 항목이 계산되지 않아 비교하지 않음.
- post-layout 시뮬에서 리셋 recovery/removal은 SDF로 검증되지 않음(STA로 대체).
- IO hold 여유 11 ps로 얇음(입력 지연 최소값 0.01 ns 모델 영향).
- 도달한 최소 클럭 주기는 미측정(10 ns만 수행). 총 실행 클럭 843은 V1 값(같은 RTL/프로그램, 재측정 안 함).
- CTS 직후 setup(+0.034 ns)은 `optDesign` Initial Summary 값이며 `timeDesign` 직후 값과 미세 차이 가능.
- 합성 5,235 → 배치 5,223 인스턴스 감소(12개) 원인 미확인(EC는 PASS).
- 합성 후 Tempus(`tempus_syn.tcl`)는 사용자 결정으로 실행하지 않음.
- V1 수치(PPT)는 로그 대조 전이라 "확인됨"으로 쓰지 않는다 (V2 수치만 로그 대조 완료).

## 6. V1 PPT/문서 정정 목록 (사용자가 수정할 것)
- 17번 슬라이드: "UART 보레이트 카운터 r_count_reg_4" → **TX FIFO 카운터** (`uut5/uut2 = tx_fifo`).
- 12번 슬라이드 서술(입력 구동을 `set_input_transition 0.1`로 교체)과 V1 `mcu_pad_top.sdc`의 실제 상태(`set_driving_cell PADDI` 활성, `set_input_transition`은 주석, SDC 주석은 "instead of PADDI"라 모순) 불일치 → 어느 SDC로 10 ns 합성이 돌았는지 확인 후 정리.
- 7, 11, 32번 슬라이드의 "병목 = 32비트 ripple-carry 가산기(약 1.67 ns)"는 20/5 ns 합성의 구조이고 **10 ns 최종 넷리스트의 가산기는 AOI 게이트열**(ADDFX1 6개). 서술을 "5 ns/20 ns 합성에서 관찰"로 한정하거나 10 ns 기준으로 교체.
- V1 pre-layout 문서의 지연 확대 캡션 "약 1.15 ns"는 캡처의 Cursor-Baseline **1.773 ns**와 불일치(다른 캡션/PPT 19번은 +1.77 ns).
- V1 문서의 "5000개 net 검사"는 진행 메시지로 보인다(전체 net 수 아님) [추정].
- V1 PnR 문서의 밀도 9.52%(checkPlace, `place_design` 직후)와 9.9%/9.878%(`place_opt` 후)는 **시점 차이**임을 캡션에 밝힐 것.
- 분량: 32장은 계획서 8장 구성(README 한 장 + 버전 페이지 + 부록)에 맞춰 요약/부록 분리 권장.

## 7. 캡션/문체 규칙 (사용자가 쓰는 형식)
- 한두 문장 평서문("~이다/한다"), **값과 시점을 포함**: `배선 후 최종 setup 타이밍(postRoute, slow 코너 SS_WORST, 클럭 10 ns): WNS +0.348 ns, TNS 0, 위반 경로 0개이다.`
- 시점/조건 구분 필수: preCTS / CTS 직후 / 최적화 후 / postRoute, SS_WORST(setup) / FF_BEST(hold), worst / best, 밀도는 어느 시점 값인지.
- 확인 못 한 것은 쓰지 않거나 "~로 보인다"로. 단정 금지.
- V1과 직접 비교하지 않는 항목(전력, 패드 관련)은 "패드가 없어 ..."라고 사유를 밝힌다.
- 전력 캡션에는 "8 ns 기준, 설계 클럭 10 ns"를 반드시 병기.

## 8. 공개 시 주의
- 캡처/로그의 터미널 프롬프트와 경로에 학교 서버의 계정 이름, 호스트 이름, 홈 디렉터리 경로가 보인다. 가릴지 그대로 둘지 사용자가 정해야 한다. (이 노트에는 실제 이름을 적지 않는다.)
- 저장소는 공개다. ARM/cmsdk 관련 파일은 올리지 않는다(과거 커밋에 `cmsdk_mcu.v`가 남아 있으나 사용자는 "중요한 부분은 암호화되어 공개돼도 괜찮다"고 판단).
- 계획서 원칙: "플로우가 돌아가는 상태까지 끝낸 버전만 공개한다. 수치는 로그 원본과 대조하기 전에는 확인됨으로 쓰지 않는다."
