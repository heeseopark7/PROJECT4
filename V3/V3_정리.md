# V3 전체 정리 (포트폴리오 작성용 자료)

이 문서는 V3 실험(가산기 구조 교체)과 V2/V3 합성 sweep, 4 ns PnR timing closure까지의 **모든 결과를 한곳에 모은 자료**다. 포트폴리오 문서/슬라이드를 만들 때 이 파일을 원본으로 쓴다.

- 진행 기록과 인수인계는 `V3/README.md`, 계획은 `V2/docs/MCU_계획서_V번호수정본.docx`, 추가 실험 계획은 `V3/PD_실험_계획.md`.
- **수치 출처 표기:** 따로 적지 않은 V3 값은 저장소 `V3/TOP` 로그 원본과 대조한 값이다. **[캡처]** 표시는 서버(저장소 밖)에서 실행해 사용자 캡처로만 확인한 값이다 (V2 sweep, V2 4 ns PnR/ECO).
- 단위: 시간 ns 또는 ps, 면적 µm²(셀 면적), 전력 mW.

## 0. 한 페이지 요약

| 항목 | 내용 |
|---|---|
| 프로젝트 | 자작 MIPS 단일 사이클 MCU(CPU, 명령어 ROM, 데이터 RAM, APB 브리지, UART, SPI master/slave)를 GPDK045로 RTL→GDS 구현하고, 버전마다 **한 가지만** 바꿔 PPA 변화를 측정·해석 |
| 도구 | Genus 22.17(합성), Conformal(EC), Innovus 22.17(PnR), Tempus 22.17(STA), Xcelium 22.03(시뮬), iverilog(RTL 회귀) |
| V3 변경 | `sccpu.v`의 ALU 덧셈/뺄셈을 32비트 Kogge-Stone prefix 가산기(`add32_ks.v`)로 교체 |
| 가설 | 최악 경로의 34%를 차지하던 가산기 구간이 줄어 더 빠른 클럭까지 닫히고, 면적은 늘어난다 |
| 판정 | **지지되지 않음.** 합성 통과 최소 주기 V2 3.9 ns, V3 3.97 ns. 같은 주기 면적은 V3가 7.7~15.9% 큼 |
| 핵심 원인 | Genus가 RTL 가산기 구조를 유지하지 않고 타이밍 제약에 맞게 재구성. 10 ns: ripple 형태(경로상 43셀, 약 3.9 ns), 빡빡한 주기: 얕은 구조(7~14셀, 약 0.8~0.9 ns). V2의 `+`/`-`도 툴이 같은 수준으로 최적화 |
| 관찰된 부분 | 한계 주기(3.97 ns)에서 최악 경로가 가산기에서 시프터로 이동 |
| 10 ns 사인오프 | setup +0.341 ns, hold +0.009 ns, DRC 0, EC PASS 2회, 게이트 시뮬 worst/best PASS (V2와 사실상 동일) |
| 4 ns PnR | 두 버전 모두 사인오프 통과. V3는 기본 플로우(+0.009 ns), V2는 기본 플로우 1 ps 미달 → **수동 ECO 셀 1개 교체**로 통과(+0.010 ns) |
| 다음 개선 대상 | 4 ns 병목은 RAM 읽기→레지스터 파일 계열과 ROM→CPU→주소 디코드→UART FIFO 계열의 경쟁. 가산기가 아니라 이 경로들(V4: 주소 디코드 레지스터화) |

## 1. 실험 설계

### 1.1 버전 체계
| 버전 | 내용 | 상태 |
|---|---|---|
| V1 | 패드 포함 칩 레벨 완성본 (`mcu_pad_top`) | 완료 |
| V2 | 패드 없는 코어 단독 기준선 (`mcu_core_top`), RTL 변경 없음 | 완료 (V3 비교 기준) |
| **V3** | **ALU 가산기 구조 교체 + 4 ns PnR closure 실험** | **완료** |
| V4 | 주소 디코드 결과 레지스터화 (V3 기반) | 다음 |
| V5, V6 | 전력/면적 축, SPI FIFO | 선택/후순위 |

### 1.2 원칙 (계획서 1장)
1. 버전마다 바꾸는 것은 한 가지뿐이다.
2. 모든 버전은 같은 SDC, 같은 플로우 스크립트로 돌린다. sweep 때만 `create_clock -period`를 바꾼다.
3. 기대와 다른 결과와 실패도 그대로 기록한다.
4. 숫자마다 "왜"를 설명할 수 있어야 한다. 로그 원본과 대조 전에는 확인된 값으로 쓰지 않는다.
5. V1(패드)과 V2 이후(코어 단독)의 슬랙/전력은 직접 비교하지 않는다.
6. 버전 페이지 5칸: 가설 / 변경 / 결과 / 해석 / 한계.

### 1.3 가설의 근거 (V2 post-route 최악 경로)
PC 레지스터 → 명령어 ROM → CPU 디코드/가산기 → 주소 디코드 → UART 레지스터 → TX FIFO. 데이터 경로 약 9.4 ns 중 **가산기 약 3.2 ns(34%)**가 가장 큰 구간이었다. 합성 넷리스트의 가산기는 ADDFX1 체인이 아니라 AOI2BB1 계열 게이트열(약 15단, 단당 약 180 ps)이었다.

### 1.4 SDC (모든 버전 동일, `3_SYN/cons/mcu_core_top.sdc`)
클럭 10 ns(sweep 때만 변경), source/network latency 0.2 ns, setup uncertainty 0.1 ns, clock transition 0.1 ns, 입력 지연 max 0.1 / min 0.01 ns, 출력 지연 max 0.1 / min −0.01 ns, input transition 0.1 ns, load 0.003(3 fF), `set_ideal_network` clk/clrn (합성용).

## 2. 변경 내용

### 2.1 RTL
```verilog
// sccpu.v (V3): add와 sub가 가산기 하나를 공유. sub = a + ~b + 1
wire [31:0] w_bx;                                   // 91번 줄
wire [31:0] w_sum;                                  // 92번 줄
assign  w_bx = w_sub ? ~w_b : w_b;                  // 160번 줄
add32_ks u_add (.a(w_a), .b(w_bx), .cin(w_sub), .sum(w_sum));   // 161번 줄
if      (w_sub) r_alu = w_sum;                      // 164번 줄 (기존 w_a - w_b)
...
else            r_alu = w_sum;                      // 172번 줄 (기존 w_a + w_b: add, addi, lw, sw)

// add32_ks.v : 32-bit Kogge-Stone
assign w_p0 = a ^ b;
assign w_g0 = {a[31:1] & b[31:1], (a[0] & b[0]) | (w_p0[0] & cin)};  // cin은 비트 0의 g에 합침
assign w_g1 = w_g0 | (w_p0 & {w_g0[30:0], 1'b0});   // 간격 1
...                                                  // 간격 2, 4, 8, 16 (prefix 5단)
assign sum  = w_p0 ^ {w_g5[30:0], cin};
```
PC+4, 분기 목표, 비교기, 다른 ALU 분기(and/or/xor/shift/lui)는 V2와 같다.

### 2.2 새 파일 때문에 불가피했던 변경
| 파일 | 변경 |
|---|---|
| `3_SYN/script/syn_mcu_core_top.tcl` | `RTL_SOURCES`에 `../1_RTL/add32_ks.v` 한 줄 |
| `4_EC/script/script.tcl` | Golden 목록에 `add32_ks.v` 한 줄 |
| `2_SIM/1_FUNCTION/run_function.tcl` | `add32_ks.v` 한 줄 + 테스트벤치 경로 오타 `../TESTBENCH` → `../4_TESTBENCH` |
| PnR SDC 처리 | V2는 별도 사본 `mcu_core_top_pnr.sdc`. V3는 mmmc가 합성 SDC(`3_SYN/mapped/...syn_final.sdc`)를 직접 읽고 그 파일의 `set_ideal_network` clk/clrn 두 줄을 주석 처리. **적용 제약은 V2와 같다** (클럭 트리 버퍼 141개로 정상 생성 확인) |

패드 없는 코어에서는 clk 포트 net이 FF를 직접 구동하므로, ideal network가 남아 있으면 CTS가 버퍼를 하나도 넣지 않는다 (V2에서 겪은 함정).

## 7. 해석과 결론
1. **가설(더 빠른 클럭까지 닫힌다)은 지지되지 않았다.** 합성 통과 최소 주기 V2 3.9 ns, V3 3.97 ns. 같은 주기 면적은 V3가 크다(4 ns +7.7%, 3.9 ns +15.9%).
2. **원인: 합성 툴이 RTL 가산기 구조를 제약에 맞게 다시 만든다.** 10 ns에서는 Kogge-Stone가 면적을 줄이는 ripple(43셀, 약 3.9 ns)로 합성되고 배선 후에도 유지(44셀, 3.98 ns, 42.7%). 빡빡한 주기에서는 얕은 구조(7~14셀, 약 0.8~0.9 ns). V2의 `+`/`-`도 같은 수준으로 최적화되어(3.75 ns에서 CPU 구간 1,667 vs 1,668 ps) RTL에서 구조를 지정한 이점이 없었다.
3. **최악 경로 이동은 관찰되었다.** V3 한계 주기(3.97 ns)에서 최악 경로가 시프터(`sll`)로, 빡빡한 주기에서는 끝점이 TX FIFO 카운터에서 FIFO 메모리로 이동.
4. **10 ns PnR에서는 차이가 거의 없다.** setup −0.007 ns, hold −0.002 ns, 코어 +1.0%.
5. **4 ns PnR에서는 두 버전 모두 사인오프 통과.** V3 기본 플로우, V2 수동 ECO 셀 1개. 같은 4 ns에서 V3는 면적·코어 +7.7%, 전력 +10.6%로 가산기 변경의 비용만 남았다.
6. **4 ns 병목은 한 경로가 아니다.** RAM 읽기 → 레지스터 파일 계열과 ROM → CPU → 주소 디코드 → UART FIFO 계열이 경계에서 경쟁(배치 직후 전자, 최종 후자). 다음 개선 대상은 가산기가 아니라 이 경로들이다 → V4(주소 디코드 레지스터화).
7. **전력 −9.2%(10 ns)는 실제 이득으로 해석하지 않는다.** 벡터 없는 정적 분석이라 논리 구조가 바뀌면 추정 활동도가 달라진다.

## 9. 한계
1. 합성 결과가 주기에 단조롭지 않아(V3 3.95 실패, 3.97 통과) 통과 최소 주기는 측정점 기준. 실패한 주기끼리의 면적 비교는 신뢰도가 낮다.
2. 합성 통과 주기는 합성 기준. PnR은 10 ns, 4 ns만 수행했고 PnR 기준 최소 주기를 더 좁히지는 않았다.
3. V2 sweep과 V2 4 ns PnR/ECO 값은 캡처 기준(로그는 서버에만). V2 sweep 복사본은 10 ns 재현으로 신뢰성 확인.
4. 전력은 정적 분석(입력 활동 0.2, 활동 주기 8 ns). 클럭 주기가 다른 결과끼리 비교 불가.
5. 테스트 프로그램에 `sub`가 없어 시뮬에서 cin=1은 단독 랜덤 테스트로만 검증.
6. IO hold 여유가 얇다(10 ns +0.009, 4 ns V2 removal +0.006 ns). 입력 지연 최소 0.01 ns 조건, FE_PHC 버퍼로 확보.
7. Tempus Design Mode 65nm 표시(공정 설정 없음, ECO 세션에서는 90nm 표시), MMMC Non-OCV, SI Off. 실무 사인오프(OCV, SI, 다중 코너)보다 느슨하다.
8. SDF-808 경고(같은 핀 쌍 arc에 같은 지연), ChipFinish 후 RouteDesign 기준 STA(필러는 타이밍 경로 없음).
9. 4 ns 게이트 시뮬 미실시(테스트벤치 `CLK_PERIOD=10`, `UART_BIT=640` 고정). STA와 EC로 확인.
10. V2 4 ns는 ECO 적용으로 V3와 플로우가 1단계 다르다.
11. PnR SDC를 mmmc 직접 참조 + 합성 SDC 주석 처리 방식으로 바꿨다(적용 제약은 V2와 같음). 재합성하면 ideal 줄이 다시 살아난다.
12. 원인 미확인: 10 ns `scinstmem` +61 µm², Unloaded Comb Pin +1, V3 4 ns 이하 FF 1,794개, V2 3 ns FF 2,072개, 4 ns 배치 후 셀 면적 −8.8%, V3 4 ns Innovus/Tempus 3 ps 차이.

## 10. 예상 질문과 답 (요지)
| 질문 | 답 |
|---|---|
| Kogge-Stone로 바꿨는데 왜 빨라지지 않았나? | 합성 툴은 RTL 구조를 그대로 매핑하지 않고 제약을 만족하는 최소 면적 구현을 찾는다. 10 ns에서는 ripple로, 빡빡한 주기에서는 V2의 `+`도 빠른 구조로 만든다. 3.75 ns에서 CPU 구간이 V2 1,667, V3 1,668 ps로 같았다 |
| V3가 오히려 0.07 ns 느린 이유는? | 차이의 대부분이 RTL을 바꾸지 않은 ROM·주소 디코드 구간에서 나왔고 결과가 단조롭지 않다. "가산기 변경의 이득이 없다"까지만 결론 낸다 |
| 가설이 틀렸는데 의미는? | RTL 수준 산술 구조 지정의 효과가 작다는 것을 측정으로 확인했고, 병목이 가산기 밖에 있다는 근거로 다음 버전(V4)을 정했다 |
| preCTS 위반 988개는 괜찮았나? | preCTS는 ideal 클럭 추정 단계. 위반이 얕고(평균 −35 ps) 넓게 퍼져 CTS 후 1개로 줄고 배선 후 최적화로 닫혔다 |
| 1 ps 위반을 어떻게 고쳤나? | 경로를 구간 분해하고 상위 경로 slack을 확인한 뒤, 끝점 직전의 가장 약한 셀(XL)을 X1로 교체. 셀 지연 23 ps + FF setup 요구 15 ps 감소로 +0.037 ns. hold와 다른 경로 영향 없음을 Tempus와 EC로 확인 |
| 전력이 10 ns에서 9% 줄었는데? | 정적 분석이라 구조가 바뀌면 추정 활동도가 달라진다. 같은 4 ns에서는 V3가 10.6% 높았다. 실제 비교에는 VCD/SAIF 활동도가 필요 |
| hold +0.009 ns는 충분한가? | 위반은 아니지만 얇다. 입력 지연 최소 0.01 ns 조건 때문에 입력·리셋 경로가 짧고, PnR이 FE_PHC 지연 버퍼로 맞췄다 |

## 11. 보여줄 수 있는 역량 (포트폴리오 포인트)
- RTL → 합성 → EC → PnR(floorplan, power plan, place, CTS, route, filler) → 사인오프 STA → SDF 게이트 시뮬을 같은 조건으로 두 버전에 수행
- 한 가지만 바꾸는 통제된 실험, 불가피한 변경까지 모두 기록, 원본을 건드리지 않는 sweep(재현성 확인)
- 경로 구간 분해와 검산(구간 합 = 도착 시각), 바뀐 모듈과 안 바뀐 모듈의 기여 구분
- 부정적 결과를 셀 수·구간 지연·면적 분해로 설명
- timing closure: 단계별 WNS 추적, 위반 경로 분석, 수동 ECO(셀 사이징), ECO 후 사인오프·EC·물리 검증
- PD 함정 관리: 코어 단독의 ideal network와 CTS, SDF 적용률(V1 0.17% 사고), IO hold 버퍼, 전력 분석 조건 고정
- PI 관점: 코어 링/스트라이프 전원망 구성과 검증, 같은 조건에서 정적 전력 비교와 그 한계
